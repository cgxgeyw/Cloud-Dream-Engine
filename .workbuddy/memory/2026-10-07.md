## 排查：会话 d83b89f0「没有回复」——既不是模型也不是提示词，是 json_object 参数

会话 `d83b89f0-9473-42b3-b257-646d1eb2f861`（同「健康生活」世界）。现象：current_line = 「（本回合没有可显示的台词）」。

实测（用库里的 api_key 直连 step-5-preview，同一提示词，只改 `response_format`）：
- `response_format={"type":"json_object"}` → `{": "  \t: null,\n "speaker":..., "content":"你好呀！...", "narration":""}`，开头多了垃圾字段，JSON 非法。
- 不带 response_format → ```` ```json {"speaker":...,"content":"...","narration":""} ``` ```` 完整合法。

线上那次模型输出的 content 是 `{"  \t":"这是一张名为…","narration":""}`——键名被吞掉，正文塞在空白键里，
且键名含**裸 tab** 导致 serde_json 严格解析也失败 → 解析器找不到 content 字段 → 降级占位文案。
注意：模型 reasoning 完全正确（准确描述了「云朵梦境」首页截图），finish_reason=stop，说明提示词是有效的。

为什么总是它：角色「健康小助手」model 字段为空 → 用 is_default=1 的 step-5-preview；
它是**唯一**开了 image/audio 模态的模型，所以发图会话必定走它。
统计：step-5-preview 调用 3 次 3 次异常（一次 `{ }`、一次 400、一次残缺 JSON），deepseek-v4-flash 35 次全正常。

修复（238 个 lib 测试全通过）：
- `src-tauri/src/services/game_engine/dialogue.rs`：新增 `salvage_longest_string_value`，
  在键名被写坏时从空白/乱码键里捞正文；先严格解析、失败再把裸 `\t`/`\r` 转义后重试
  （裸控制字符会让 serde_json 直接失败）；**只认「键名 trim 后为空或不含 ASCII 字母数字」**的条目，
  正常键名一律不碰——否则会把 `advance_objective` 这类结构化指令当台词外泄（已有一个既有测试正是守这条）。
- 新增 3 个单测（mangled keys / 优先命名字段 / narration-only 不捞）。

根治方案：用户选了 1，已实现。
